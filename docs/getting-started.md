# 入门详解

本文对应 README 的四步流程，解释每一步在做什么，以及为什么这样设计。只做配置同步的话，读完这一页就够了。

## 0. 一套配置是怎样走到另一台设备的

```text
配置源（Git 仓库）
  common/            公共规则，所有设备共用
  codex/config.toml    选定的 Codex 共享字段
  claude/settings.shared.json  选定的 Claude 共享字段
        │
        │  sync（拉取 → 解析 → 备份 → 应用 → 核对）
        ▼
本机目标文件
  CODEX_HOME/AGENTS.md          受管区块
  CODEX_HOME/config.toml        选定字段
  CLAUDE_CONFIG_DIR/CLAUDE.md   受管区块
  CLAUDE_CONFIG_DIR/settings.json  选定字段
```

“配置相同”指**受管共享字段和规则一致**。本机路径、平台专属值、凭据、未选中的工具设置本来就可以不同，不算差异。

## 1. 首次设置

```text
.\ai-config.ps1 setup          # Windows
./ai-config.command setup      # macOS
```

不带 `--apply` 时是**纯只读检测**，会输出：

- 当前系统（windows / macos）
- Python 版本和是否满足 3.11+
- Git 是否可用
- Codex / Claude 目录在哪，来自环境变量（`CODEX_HOME` / `CLAUDE_CONFIG_DIR`）还是默认位置

检测**不会创建**任何工具目录。没装某个工具就如实报告，不会替你造一个空的配置目录出来。

确认后加 `--apply`：

```text
.\ai-config.ps1 setup --apply
```

它会生成 `device.json`（已被 Git 忽略，不会提交）：

| 字段 | 含义 |
| --- | --- |
| `device` | 本机设备 ID，如 `windows-a`。三台设备必须不同 |
| `state_dir` | 本机基线和备份，**不同步、不删除** |
| `memory_repo` | 记忆仓库路径，必须在配置源之外。不用记忆时留占位即可 |
| `codex` / `claude` | 工具配置目录 |
| `codex_keys` / `claude_keys` | 选中的共享字段 |
| `*_overrides` | 只属于本机的参数，不填凭据 |

已经存在 `device.json` 时，写入前会先备份，并打印备份路径。

### 共享范围怎么选

- **仅公共规则**（`rules_only`，默认）：只统一 `common/` 下的规则，工具参数保持各设备原样。最保守。
- **公共规则 + 选定工具设置**：额外统一你勾选的字段，例如 Codex 的命令审批策略。

未勾选的字段完全不受影响。工具的 MCP、提供商、Windows 沙箱等设置保持本机值。

## 2. 加入第二台设备

在第二台机器上克隆同一个配置源，运行同样的 `setup --apply`。

- 设备 ID 自动生成，与已有设备冲突时会**明确停止**，不会覆盖已有设备记录。
- 网络或认证失败时已填写的信息会保留，可以直接重试。
- 日志里不输出带凭据的 URL。

重复运行是幂等的，不会产生半套配置。

## 3. 日常同步

```text
.\ai-config.ps1 sync                          # 预览
.\ai-config.ps1 sync --apply                  # 应用
.\ai-config.ps1 sync --fetch --apply          # 先下载配置源，再应用
.\ai-config.ps1 sync --publish --apply        # 先把本机保存的共享修改发布出去，再应用
```

执行的阶段依次是：

1. **本机漂移检查** — 目标文件的受管内容是否被工具或手工改过。
2. **获取远端** — 加 `--fetch` 时从**配置源**（ai-config 仓库）快进拉取。只快进，不强制合并。
3. **发布共享修改** — 加 `--publish` 时把本机保存的共享修改（`common/`、`codex/`、`claude/`）提交并推送到配置源远端。
4. **解析共享变更** — 算出共享值应该写成本机什么样子。
5. **预览** — 不带 `--apply` 时到此为止，**不写任何文件**，也不发布、不上报。
6. **备份并应用** — 先写入事务日志和备份，再改文件。
7. **目标核验** — 重新读取目标文件，确认受管内容已经是期望值。
8. **状态上报** — 本机配置里记录了配置源地址时，把回执上报到配置源的 `device-receipts` 分支。

失败时会明确说是**哪个阶段**出的问题（下载、发布、解析、应用还是核验），对应不同的错误编号和退出码。

### 关于“保存”“发布”“应用”和“生效”

这是四件不同的事：

| 说法 | 含义 |
| --- | --- |
| 本机保存 | 共享值已经写进本机配置源副本的工作区，还没有离开这台机器 |
| 发布完成 | 共享修改已提交并推送到配置源远端，其他设备下载后能看到 |
| 下载完成 | 文件已经从配置源取回本机 |
| 应用完成 | 目标文件已经写入并核对一致 |
| 会话已重新加载 | 工具重开后才真正使用新设置 |

脚本只保证前四件，而且每次同步都会分别打印这四行结果。需要重开工具时会单独提示，不会替你宣称已经生效。

`--publish` 只提交 `common/`、`codex/`、`claude/` 三个目录，不会把你配置源里其它未提交的工作一起提交。推送失败时本机提交会保留，不会强制覆盖远端。

### 零变更也是正常结果

如果本机已经和共享值一致，同步会显示“没有需要写入的变化”并重新核对目标文件。**零变更预览不等于已生效**，也不代表远端没有新内容——加 `--fetch` 才会去拉取。

核验没有全部通过时不会写入“最近成功应用”记录，下一次同步也不会把这种文件当成已应用。

## 4. 确认状态

```text
.\ai-config.ps1 status
```

会分三块列出：

- **配置**：本机状态、每个目标文件的核验结果、最近成功应用时间。
- **记忆**：是否启用。没启用就明确写“未启用”，不会因此报错。
- **项目接续**：是否登记了项目。

“其他设备”一节只显示对方**最近报告于某时刻**。离线设备不会被标成“在线”或“实时一致”——回执是上次上报的快照，不是实时连接。

状态词的含义：

| 状态 | 含义 | 要做什么 |
| --- | --- | --- |
| 未设置 | 还没有配置或目标文件不存在 | 运行 `sync --apply` |
| 待同步 | 共享有更新或目标文件尚无受管区块 | 运行 `sync --apply` |
| 已应用 | 目标文件的受管内容与共享值一致 | 无需操作（如需重开工具会另有提示） |
| 存在本机修改 | 受管内容被本机改过 | 运行 `diff` 选择归属 |
| 冲突 | 双方都改了同一处 | 运行 `diff`，再重新同步 |
| 离线 | 无法连接配置源 | 恢复网络后重试 |
| 应用失败 | 目标缺失、格式错误或无法读取 | 查看 `doctor` 输出 |
| 需要重启 | 已应用但工具尚未加载 | 重开工具 |
